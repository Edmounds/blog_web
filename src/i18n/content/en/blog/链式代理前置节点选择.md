## How to Choose a Front Node for a Chained Proxy
A chained proxy consists of a front node and an exit node.

The core principle behind choosing a front node is that it should act as a purely transparent TCP transport tunnel.
Many protocols work well for direct connections, but can cause severe disconnections or freezes when used as front nodes.
### Recommended Front-End Protocols

| Rating | Protocol Type | Technical Characteristics |
| :-----: | :------------------ | :------------------------- |
| **Top choice** | **Shadowsocks ** | Pure TCP encrypted byte stream, with no certificate handshake or multiplexing interference |
| **Recommended** | **Trojan (native TCP)** | A single-layer, standard TLS encrypted tunnel with a clean, standard handshake |
| **Recommended** | **VMess (pure TCP)** | Basic symmetric encryption for transport (disable WS and CDN) |
| **Avoid** | **Hysteria / TUIC** | Based on the UDP / QUIC protocol stack |
| **Avoid** | **VLESS-Reality** | XTLS-Vision flow-control checks and certificate-stealing mechanism |
| **Avoid** | **Any node behind a CDN** | Routed through an edge reverse proxy such as Cloudflare |

Once you’ve chosen a protocol, consider latency and location.
A quick note on location: choose a combination with the shortest physical route. Suppose your residential-broadband exit node is on the US West Coast. You wouldn’t want to choose a node in Europe or India, because that would add a lot of unnecessary physical distance and latency. From mainland China, it’s best to choose a node in Hong Kong, Japan, or Singapore. The rest of the route will generally run over trans-Pacific submarine cables to the US West Coast.

In short, choose a low-latency Asia-Pacific node that uses a suitable protocol as your front node.
### Why Do Advanced Protocols Frequently Disconnect When Used as Front Nodes?

1. **UDP / QUIC protocols cannot be nested reliably**
The client carries a TCP handshake for residential broadband inside a UDP tunnel, making the underlying state machine complicated to handle. The two layers of congestion control compete and conflict, causing frequent connection resets.
**Protocols involved**: Hysteria 1/2, TUIC, WireGuard.

2. **Reality / Vision flow control conflicts with the inner handshake**
Reality simulates a real website’s TLS handshake. Nesting a second proxy handshake inside the tunnel (such as SOCKS5 or a second TLS handshake) contaminates the traffic characteristics, triggering filtering and blocking by the Vision module’s flow-control checks and directly returning RST to the client.
**Protocols involved**: VLESS-Reality, VLESS-XTLS-Vision.

3. **WebSocket + CDN timeouts**
CDN edge nodes impose strict timeouts on connections to the origin. If the front connection to a slow residential-broadband gateway times out, the CDN returns a 502 or 504 Gateway Timeout.
**Protocols involved**: WS or gRPC nodes behind Cloudflare CDN.

## Comparison of Common Front-Node Protocols

Front-node connections operate in environments with public-network censorship and internal network monitoring, so encryption strength and resistance to traffic inspection are key concerns.

| Protocol / Type | Transport Layer | Encryption | Camouflage and Resistance to Blocking |
| :-------------------- | :--------- | :--------------------------------- | :--------------------------- |
| **HTTP Proxy** | TCP | **None** | No camouflage. Plain-text content that gateways can match directly with regular expressions |
| **SOCKS5** | TCP / UDP | **None** | No camouflage. Fixed hexadecimal handshake signature (`05 01 00`) |
| **Shadowsocks** | TCP / UDP | **Strong symmetric encryption** (AES-256-GCM / ChaCha20) | Purely random ciphertext. No plaintext protocol fields, but easily matched by fingerprint databases |
| **VLESS-Reality** | TCP | **Strong TLS 1.3 encryption** (public-key authentication) | Very high. Borrows the SNI of a real external website, eliminating certificate signatures |
| **Trojan** | TCP | **Standard TLS 1.3 encryption** (CA certificate) | High. The password is embedded in the TLS payload, making the traffic look like legitimate HTTPS |
| **Hysteria 2 / TUIC** | UDP (QUIC) | **Strong TLS 1.3 encryption** | Camouflaged as HTTP/3 traffic or random UDP data |
> Note: HTTP proxies do not encrypt the transport layer. Intermediate network devices can capture packets and read request headers, full URL paths, cookies, and account credentials.
