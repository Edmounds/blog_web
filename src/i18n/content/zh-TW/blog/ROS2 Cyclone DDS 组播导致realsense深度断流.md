## 案件回顧

### 前情摘要

容我介紹一下這兩位犯罪嫌疑人：

- MID-360 雷射雷達｜有線網路埠，實際協商速率 100 Mbps
- Intel RealSense D435if 深度攝影機｜USB 3.0

之前在 ROS 2 Humble 的專案裡，我遇到了 Action 與 Service 偶發沒有回應的問題：任務狀態機拿不到 Goal Handle，比賽流程就卡住了。為了繞開這個問題，我把 ROS 2 的通訊中介軟體 DDS 從預設的 Fast DDS 換成了 Cyclone DDS；同時，為了減少影像搬運的開銷，我還將相機驅動節點與 YOLO 推論節點編譯為 ROS 2 元件，載入到同一個元件容器行程中。

### 東窗事發

原本一直測試都沒問題，甚至在出發前一天就調好第一版了。照當時的測試成績，我們覺得進國一很有希望。大家都開香檳了，以為終於打破了做專案總要到 DDL 極限才調完的詛咒。可惜高興得太早，該來的還是要來。

流程已經最佳化得差不多了，我就想著改一下比賽除錯工具。為了在現場更直觀地看到相機畫面，我大幅改寫了之前做的一個 Web 除錯網頁中的影片串流元件，功能有點像 RViz。為了實現低延遲並控制位元率，我選擇了 WebRTC：ROS 2 端執行一個獨立的伺服器節點，訂閱相機的 RGB 與深度影像，將用於顯示的畫面編碼為 H.264 後，再透過 WebRTC 傳送到我的電腦。單獨測試時，效果符合預期，但問題恰恰就藏在這個「獨立」裡——我在元件容器外面增加了一個跨行程訂閱者。相機到 YOLO 的本機路徑雖然還在，發布者卻得額外透過 DDS 將原始影像交付給這個新行程，而 WebRTC 的壓縮發生在收到影像之後，救不了前面的這段傳輸。

### DEBUG

出發前的 4 個小時，埋下的雷集中爆發了。除錯工具完善後，我準備再跑一遍完整流程，結果車能動，目標卻一個也沒辨識出來，一看日誌，YOLO 推論節點壓根沒有正常開始推論。「好嘛，重啟一下行程，應該有 90% 的機率能解決吧。」壞了，沒解決。「那我就 AI 啟動吧。」AI 看了日誌，說是深度資料短暫出現後又斷開，推測相機線鬆了。我鬆了一口氣，線鬆了好辦啊，重新插拔一下不就行了。壞了，還是不行，換線、換 USB 連接埠、換 Thunderbolt 連接埠一輪試下來都沒用。我又輪番試了 `gemini-3.8-flash`、`gpt-6.1-sol`、`gpt-6-astra`，當時它們都沒有抓到問題，反而亂改現有程式碼，一度連 RGB 都沒了。

眼看離出發只剩一個小時，問題依然沒解決，最後只能 `git reset` 退回昨天跑通的程式碼。我想，只要舊版本能跑，就能說明這套硬體沒有壞，結果居然還是沒跑通——後來才知道，WebRTC 配套節點放在另一個工作區，這次回退根本沒動到它。但當時我不知道，真的覺得天塌了。軟體問題還有救，硬體壞了就真的沒轍，這會兒也找不出第二台相機，只能開始收拾東西，走吧走吧，又回到了那句「老師，我們有跑通的影片」。

去機場的路上，我很睏，卻睡不著。凌晨五點的高架空曠得出奇，路燈在破曉前的夜色裡連成一線，沒有人說話，也沒有能繼續除錯的車，我只能坐著，什麼也碰不到，什麼也改不了。出發前那幾個小時幾乎把人逼瘋的焦躁，反而在這陣沉默裡慢慢消退了。剛才一直急著靠重啟、換線、求助 AI 碰運氣，想在下一秒就把火撲滅，卻連最基本的控制變數都沒做好。「不能再依賴那個傻福 AI 了。」我得先用 `realsense-viewer` 單獨查看 RGB 和深度，把 ROS 的影響排除掉。

抵達登機門時，離登機還有半小時。我趕忙替車裝上電池測試，終於拿到一個好消息：單獨查看相機時，RGB 和深度都正常。說明硬體是沒毛病的，是軟體問題，還有救。

到了飯店，房間太窄，沒辦法跑完整流程，我只啟動了相機和推論節點，雷達和下位機都沒開。欸，相機居然正常了，深度和 RGB 都有。這個時候我還沒意識到差別在雷達，畢竟出發前的除錯裡它一直開著。於是我又半場開香檳，以為是什麼玄學問題，既然好了就先不管，安心睡了一會兒，等下午去現場除錯。

結果一進場館，一啟動完整流程，相機又掛了，深度依然斷流。這時我才想起中午沒有開雷達和下位機，開始逐一比對後，範圍終於縮小了：只要雷達上電並接入小電腦，相機深度就會中斷。我把現象告訴 gemini-3.8-flash，哈基米又開始應激，說可能是雷達的紅外光干擾了相機。我想，那天確實改過機械手臂的初始位置，雷達有可能掃到相機，而 D435 系列採用主動式雙目深度方案，也有紅外線投射器，光學干擾確實值得排查，於是我們把相機抬高，又用手遮住雷達測試，斷流仍然存在。直到換 gpt-6.1-sol 分析日誌，排查方向才終於轉到網路上：相機透過 USB 接入，並不代表 ROS 影像只走 USB，跨行程的原始影像流量可能正在經過雷達所在的百兆有線介面。後續限制 DDS 的業務組播後，深度恢復，網路埠傳送速率也明顯下降，這才把問題落到了通訊設定上。

## 根因剖析與傳輸機制

### 問題分析

現場最有力的證據，是故障與有線介面接入狀態、DDS 組播策略之間的對應關係：接上雷達網路後斷流，將 `AllowMulticast` 改為 `spdp` 後恢復，實體介面的傳送速率也從約 100 Mbps 降到 0.003 Mbps。這支持了**高頻寬影像透過 DDS 資料組播進入百兆鏈路，造成通訊壅塞**的解釋。

我換成 Cyclone DDS 後沒有立即遇到問題，是因為當時的通訊拓撲還比較簡單：相機與 YOLO 位於同一個容器行程內，在設定正確的情況下兩者可以走行程內通訊；後來新增的 WebRTC 節點在另一個行程中，需要透過 RMW/DDS 接收原始影像，於是多了一條高頻寬傳輸路徑（原本的行程內路徑並沒有因此失效）。Cyclone DDS 會根據介面能力、設定和發現到的對端選擇網路路徑。現場日誌中，無線介面出現過 `presumed flaky multicast, use for SPDP only`，有線介面則出現過 `presumed robust multicast support, use for everything`。這反映的是它對介面組播能力的預設判斷——無線介面傾向於只使用發現組播，有線介面則允許更廣泛地使用組播；這不等於「所有有線介面都會承載全部業務流量」，實際選擇還受版本、設定與訂閱拓撲影響。問題在於，允許資料組播的介面不一定有足夠頻寬：1280 × 720 的 RGB8 影像以 30 Hz 發布，僅像素有效負載就約為 664 Mbps，已經遠超這條 100 Mbps 鏈路，自然就會卡住。

![ROS 2 同機影像通訊與組播策略](https://img.muelsyse.us/bed/paper-20261110-ros-data-path-4c6bb401b377.png)

*圖 2：外部訂閱者增加了 DDS 影像傳輸路徑。改為 `spdp` 後，組播只用於參與者發現，端點匹配與影像傳輸使用單播；同機目的位址通常由本機路由交付，遠端訂閱者仍需要實體網路。*

> 還有一個反直覺的地方：資料明明已經透過 USB 進入同一台電腦，為什麼還會影響實體網路埠？因為跨行程通訊不會自動等於共享記憶體通訊。這裡使用的 DDS 網路路徑會把影像序列化後送入 UDP/IP 堆疊。向本機位址傳送單播時，Linux 通常透過本機路由交付；資料組播則可以同時產生面向實體介面的流量和本機回環交付。

## 解決方案

這次有效的修復，是把 Cyclone DDS 的組播限制在參與者發現階段，讓端點匹配和業務資料使用單播。在啟動 ROS 節點的終端機中設定：

```bash
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><AllowMulticast>spdp</AllowMulticast></General></Domain></CycloneDDS>'
```

也可以把它寫入 `~/.bashrc` 或 `~/.zshrc`，重新載入設定後再啟動相關節點。已經執行的行程不會自動取得新的環境變數，需要重新啟動；若節點由 systemd、容器或其他啟動器管理，也要在對應的啟動環境中傳入該變數。

`AllowMulticast` 取值說明

| 取值      | 行為與注意事項                                                              |
| :------ | :------------------------------------------------------------------- |
| `true`  | 允許發現與使用者資料使用組播；是否實際使用還取決於介面和對端情況。在頻寬受限的網路上，需要檢查影像等大型話題的傳輸路徑。           |
| `false` | 停用該設定所控制的組播。預設的組播發現路徑不可用，可透過 `Peers` 等單播發現設定建立聯繫；不能概括為「任何節點發現都會徹底失效」。 |
| `spdp`  | 僅保留 SPDP 參與者發現組播，端點匹配和業務資料使用單播。本例中，它保留了方便的節點發現，也避免了向百兆介面傳送影像資料組播。    |

## 附錄

### 理論計算

#### 影像有效負載與百兆頻寬極限計算

當時一個很有用的線索，是 RGB 接收頻率只有 4.4 Hz 左右。從單幀大小反推，它的有效負載吞吐量已經接近 100 Mbps；實體網路埠的協商速率也恰好是 100 Mbps。這與鏈路成為瓶頸的解釋相符，但這個計算本身不能替代封包擷取或介面計數器。

| 影像串流 | 解析度 | 像素編碼 | 單幀資料量 | 30 Hz 理論頻寬 |
| :--- | :--- | :--- | :---: | :---: |
| RGB | 1280 × 720 | RGB8（3 B/pixel） | 2.76 MB | **663.55 Mbps** |
| 原生深度 | 848 × 480 | Z16 / 16UC1（2 B/pixel） | 0.81 MB | **195.38 Mbps** |
| 對齊深度 | 1280 × 720 | 16UC1（2 B/pixel） | 1.84 MB | **442.37 Mbps** |

小電腦網路介面與雷達的實際協商速率為 **100 Mbps 全雙工**。全雙工表示兩個方向可以同時傳輸，並不會把單方向上限變成 200 Mbps。在不計任何協定開銷的理想情況下，它單方向最多容納：

$$100,000,000 \text{ bps} \div (1280 \times 720 \times 3 \times 8 \text{ bits}) \approx 4.52 \text{ fps}$$

現場 RGB 接收頻率為 **4.4 Hz**，換算出的像素有效負載約 **97.3 Mbps**，接近這一理論上限。

#### 實測資料對照驗證

| 監測指標 | 修復前 | 修復後 |
| :--- | :---: | :---: |
| **彩色影像更新率** | 4.4 Hz | 13.9 Hz |
| **原生深度更新率** | 0 Hz | 29.7 Hz |
| **對齊深度更新率** | 0 Hz | 14.2 Hz |
| **RGBD 心跳頻率** | 0 Hz | 14.1 Hz |
| **彩色影像接收延遲中位數** | 943.9 ms | 58.3 ms |
| **原生深度接收延遲中位數** | N/A | 42.1 ms |
| **實體有線網路埠傳送速率** | 約 100 Mbps | **0.003 Mbps** |

恢復通訊不等於每路都跑滿 30 Hz：原生深度恢復到 29.7 Hz，但 RGB、對齊深度與 RGBD 心跳仍在 14 Hz 左右。這個結果說明斷流得到了緩解，不能據此聲稱整個視覺處理鏈路已經沒有其他瓶頸。

### DDS 介紹

![ROS 2 通訊分層與行程內路徑](https://img.muelsyse.us/bed/paper-20261110-ros-layers-24212fd3eca3.png)

*圖 5：ROS 2 的用戶端函式庫、RMW 與 DDS 通訊分層。符合條件的行程內路徑可以繞過 DDS 序列化；跨行程是否使用網路或共享記憶體，取決於所選實作及設定。*

DDS（Data Distribution Service）是 OMG 發布的分散式資料通訊標準。ROS 2 通常藉助 DDS 提供發現、發布訂閱和 QoS 等能力，透過 Topic 與資料型別組織通訊，並使用 **RMW（ROS Middleware Interface）** 將用戶端 API 與具體的中介軟體實作分開，從而能在介面支援的範圍內切換實作。與 ROS 1 常用的集中式 Master 發現方式相比，DDS 可以透過分散式發現建立端點聯繫（不過，ROS 1 的 Master 也不是所有業務資料的轉送中心；節點建立連線後，業務資料通常直接傳輸，不能把 Master 故障等同於所有既有資料連線立即中斷）。DDS 實作之間通常透過 RTPS 互通，UDP/IP 是常見傳輸方式，但 DDS 標準並非只允許這一種傳輸方式。

### Fast DDS vs Cyclone DDS

下表只整理與本次問題有關的差異，不依據這次現場經歷為兩種實作劃分絕對的適用情境。

| 評估維度 | Fast DDS | Cyclone DDS |
| :--- | :--- | :--- |
| 共享記憶體 | 支援共享記憶體傳輸與資料共享等機制；是否啟用、是否減少序列化或複製，取決於版本、設定和訊息條件。 | 支援情況與版本、建置及設定有關；本文不能把「同機通訊」直接視為已啟用共享記憶體。 |
| 網路介面與組播 | 可設定網路傳輸、發現與組播行為，應檢查實際生效的設定。 | 有介面選擇和組播策略設定；本次透過 `AllowMulticast=spdp` 避免了業務資料組播。 |
| 本專案遇到的現象 | 曾遇到 Action / Service 不回應，未保留足夠資料確認具體機制。 | 外部影像訂閱與百兆有線介面加入後出現斷流，限制業務組播後恢復。 |
| 選型與驗證 | 應驗證具體版本下的功能、QoS、負載和故障復原。 | 同樣需要在完整節點拓撲與實際網路條件下驗證，不能只測單個節點。 |

### ROS 2 元件

ROS 2 元件將節點實作編譯為可動態載入的函式庫，由元件容器在同一個行程中載入。它提供共用的位址空間，便於組織節點，也為減少影像複製創造了條件，但容器如何排程回呼還取決於所選執行器，不能一概等同於「共用一個執行緒池」。相機發布、影像前處理、YOLO 推論這類連續處理大型訊息的節點，很適合檢查能否放入同一個容器中；不過，**元件化與行程內通訊是兩個相關但不同的設定點**，除了把節點放在一起，還要為相關節點啟用 `use_intra_process_comms`，並確認訊息與 QoS 支援這條路徑。

#### 元件化加速原理

滿足行程內通訊條件時，訊息可以透過 C++ 物件的所有權轉移或共享方式，交付給本機訂閱者，從而減少兩類開銷：

1. **訊息複製**：使用相容的發布與訂閱介面時，可以轉移 `std::unique_ptr` 或共享唯讀訊息；是否仍需複製，取決於訂閱者數量、回呼簽章和緩衝策略。
2. **序列化**：本機行程內交付可以繞過 DDS 的序列化與反序列化。若同時存在外部訂閱者，發布者仍需為外部路徑準備中介軟體訊息。

因此，「元件一開就完全零拷貝」不成立。要驗證實際效果，可以參考 ROS 2 的行程內通訊範例檢查訊息位址，再結合實際負載測量 CPU 使用量、記憶體頻寬和端到端延遲。

### 單播

單播會將資料傳送給特定目的位址。在本文的同機情境中，傳送至本機位址的資料通常可由本機路由交付，傳送至遠端主機則仍要使用實體鏈路。單播不會自動保證高吞吐量或低延遲，如果存在許多遠端訂閱者且需要分別傳送資料時，總流量反而可能增加；它在本例中的收益來自避免高頻寬業務組播進入受限介面。

### 組播

IPv4 組播使用 `224.0.0.0` 至 `239.255.255.255` 位址範圍。傳送端向組播群組傳送資料，網路設備按照組播轉送設定處理，接收端透過加入組播群組來接收；交換器是否只向有成員的連接埠轉送，還與 IGMP snooping 等功能有關，未啟用或設定不當時，流量可能被泛洪到更多連接埠。組播適合一對多傳輸，但仍然受鏈路頻寬、無線環境和端點實作限制。
