## 案件回顾

### 前情摘要

容我介绍一下这两位犯罪嫌疑人：

- MID-360 激光雷达｜有线网口，实际协商速率 100 Mbps
- Intel RealSense D435if 深度摄像头｜USB 3.0

之前在 ROS 2 Humble 的项目里，我遇到了 Action 与 Service 偶发不响应的问题：任务状态机拿不到 Goal Handle，比赛流程就卡住了。为了绕开这个问题，我把 ROS 2 的通信中间件 DDS 从默认的 Fast DDS 换成了 Cyclone DDS；同时，为了减少图像搬运的开销，我还将相机驱动节点与 YOLO 推理节点编译为 ROS 2 Component，加载到同一个组件容器进程中。

### 东窗事发

本来一直测试都没毛病，甚至在出发前一天就调完了第一版。按当时的测试成绩，我们觉得进国一很有希望。大家都开香槟了，以为终于打破了做项目总是 DDL 极限调完的诅咒。可惜高兴得太早，该来的还是要来。

流程已经优化得差不多了，我就想着改一下比赛调试工具。为了在现场更直观地看到摄像头画面，我大改了之前做的一个 Web 调试网页的视频串流组件，功能有点像 RViz。为了实现低延迟并控制码率，我选择了 WebRTC：ROS 2 端运行一个独立的 Server 节点，订阅相机的 RGB 和深度图，将用于显示的画面编码为 H.264 后再通过 WebRTC 发到我的电脑。单独测试时，效果符合预期，但问题恰恰就藏在这个“独立”里——我在 Component 容器外面增加了一个跨进程订阅者。相机到 YOLO 的本地路径虽然还在，发布者却得额外通过 DDS 向这个新进程交付原始图像，而 WebRTC 的压缩发生在收到图像之后，救不了前面这段传输。

### DEBUG

临近出发的前 4 个小时，埋下的雷集中爆发了。调试工具完善后，我准备再跑一遍全流程，结果车能动，目标却一个也没识别出来，一看日志，YOLO 推理节点压根没有正常开始推理。“好嘛，重启一下进程，应该有 90% 的概率能解决吧。”坏了，没解决。“那我就 AI 启动吧。”AI 看了日志，说是深度数据短暂出现后又断开，推测相机线松了。我松了一口气，线松了好办啊，拔插一下不就行了。坏了，还是不行，换线、换 USB 口、换雷电口一圈试下来都没用。我又轮番试了 gemini-3.8-flash、gpt-6.1-sol、gpt-6-astra，当时它们都没有抓到问题，反而乱改现有代码，一度连 RGB 都没了。

眼看还剩一个小时出发，问题依然没解决，最后只能 `git reset` 退回昨天跑通的代码。我想，只要旧版本能跑，就能说明这套硬件没有坏，结果居然还是没跑通——后来才知道，WebRTC 配套节点放在另一个工作区，这次回退根本没动到它。可当时我不知道，真觉得天塌了。软件问题还有救，硬件坏了就真没招，这会儿也找不出第二个摄像头，只能开始收拾东西，走吧走吧，又回到了那句“老师，我们有跑通的视频”。

去机场的路上，我很困，却睡不着。凌晨五点的高架空旷得出奇，路灯在破晓前的夜色里连成一线，没有人说话，也没有能继续调的车，我只能坐着，什么也碰不到，什么也改不了。出发前那几个小时几乎把人逼疯的焦躁，反倒在这阵沉默里慢慢消退了。刚才一直急着靠重启、换线、求助 AI 碰运气，想在下一秒就把火扑灭，却连最基本的控制变量都没做好。“不能再依赖那个傻福 AI 了。”我得先用 `realsense-viewer` 单独看 RGB 和深度，把 ROS 的影响排除掉。

抵达登机口时，离登机还有半小时。我赶忙给车装上电池测试，终于拿到一个好消息：独立查看相机时，RGB 和深度都正常。说明硬件是没毛的，是软件问题，还是有救的。

到了酒店，房间太窄，没法跑全流程，我只启动了相机和推理节点，雷达和下位机都没开。诶，相机居然正常了，深度和 RGB 都有。这个时候我还没意识到区别在雷达，毕竟出发前的调试里它一直开着。于是我又半场开香槟，以为是什么玄学问题，既然好了就先不管，安心睡了一会儿，等下午去现场调试。

结果进了场馆，一开全流程，相机又寄了，深度依然断流。这时我才想起中午没有开雷达和下位机，开始逐个对照后，范围终于缩小了：只要雷达上电并接入小电脑，相机深度就会中断。我把现象告诉 gemini-3.8-flash，哈基米又开始应激，说可能是雷达的红外光干扰了相机。我想，那天确实改过机械臂的初始位置，雷达有可能扫到相机，而 D435 系列采用主动双目深度方案，也有红外投射器，光学干扰确实值得排查，于是我们抬高相机，又用手遮挡雷达测试，断流仍然存在。直到换 gpt-6.1-sol 分析日志，排查方向才终于转到网络上：相机通过 USB 接入，并不代表 ROS 图像只走 USB，跨进程的原始图像流量可能正在经过雷达所在的百兆有线接口。后续限制 DDS 的业务组播后，深度恢复，网口发送速率也明显下降，这才把问题落到了通信配置上。

## 根因剖析与传输机理

### 问题分析

现场最有力的证据，是故障与有线接口接入、DDS 组播策略之间的对应关系：接上雷达网络后断流，将 `AllowMulticast` 改为 `spdp` 后恢复，物理接口的发送速率也从约 100 Mbps 降到 0.003 Mbps。这支持了**高带宽图像通过 DDS 数据组播进入百兆链路，造成通信拥塞**这一解释。

我换成 Cyclone DDS 后没有立即遇到问题，是因为当时的通信拓扑还比较简单：相机与 YOLO 在同一个容器进程内，配置得当时两者可以走进程内通信；后来新加的 WebRTC 节点在另一个进程，需要通过 RMW/DDS 接收原始图像，于是多出了一条高带宽传输路径（原来的进程内路径并没有因此失效）。Cyclone DDS 会根据接口能力、配置和发现到的对端选择网络路径。现场日志中，无线接口出现过 `presumed flaky multicast, use for SPDP only`，有线接口则出现过 `presumed robust multicast support, use for everything`。这反映的是它对接口组播能力的默认判断——无线接口倾向于只使用发现组播，有线接口允许更广泛地使用组播；这不等于“所有有线接口都会承载全部业务流量”，实际选择还受版本、配置与订阅拓扑影响。问题在于，允许数据组播的接口并不一定有足够带宽：1280 × 720 的 RGB8 图像按 30 Hz 发布，仅像素有效载荷就约为 664 Mbps，已经远超这条 100 Mbps 链路，自然就会卡住。

![ROS 2 同机图像通信与组播策略](https://img.muelsyse.us/bed/paper-20261110-ros-data-path-4c6bb401b377.png)

*图 2：外部订阅者增加了 DDS 图像传输路径。改为 `spdp` 后，组播只用于参与者发现，端点匹配与图像传输使用单播；同机目的地址通常由本地路由交付，远端订阅者仍需要物理网络。*

> 还有一个反直觉的地方：数据明明已经通过 USB 进入同一台电脑，为什么还会影响物理网口？因为跨进程通信不自动等于共享内存通信。这里使用的 DDS 网络路径会把图像序列化后送入 UDP/IP 栈。向本机地址发送单播时，Linux 通常通过本地路由交付；数据组播则可以同时产生面向物理接口的流量和本机回环交付。

## 解决方案

这次有效的修复，是把 Cyclone DDS 的组播限制在参与者发现阶段，让端点匹配和业务数据使用单播。在启动 ROS 节点的终端中设置：

```bash
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><AllowMulticast>spdp</AllowMulticast></General></Domain></CycloneDDS>'
```

也可以把它写入 `~/.bashrc` 或 `~/.zshrc`，重新加载配置后再启动相关节点。已经运行的进程不会自动获得新环境变量，需要重启；若节点由 systemd、容器或其他启动器管理，也要在对应启动环境中传入该变量。

`AllowMulticast` 取值说明

| 取值      | 行为与注意事项                                                              |
| :------ | :------------------------------------------------------------------- |
| `true`  | 允许发现和用户数据使用组播；是否实际使用还取决于接口和对端情况。在带宽受限的网络上，需要检查图像等大话题的传输路径。           |
| `false` | 禁用该配置所控制的组播。默认的组播发现路径不可用，可通过 `Peers` 等单播发现配置建立联系；不能概括为“任何节点发现都彻底失效”。 |
| `spdp`  | 仅保留 SPDP 参与者发现组播，端点匹配和业务数据使用单播。本例中，它保留了方便的节点发现，也避免了向百兆接口发送图像数据组播。    |

## 附录

### 理论计算

#### 图像有效载荷与百兆带宽极限计算

当时一个很有用的线索，是 RGB 接收频率只有 4.4 Hz 左右。按单帧大小反推，它的有效载荷吞吐已经接近 100 Mbps；物理网口的协商速率也恰好是 100 Mbps。这与链路成为瓶颈的解释相符，但这个计算本身不能替代抓包或接口计数器。

| 图像流 | 分辨率 | 像素编码 | 单帧数据量 | 30 Hz 理论带宽 |
| :--- | :--- | :--- | :---: | :---: |
| RGB | 1280 × 720 | RGB8（3 B/pixel） | 2.76 MB | **663.55 Mbps** |
| 原生深度 | 848 × 480 | Z16 / 16UC1（2 B/pixel） | 0.81 MB | **195.38 Mbps** |
| 对齐深度 | 1280 × 720 | 16UC1（2 B/pixel） | 1.84 MB | **442.37 Mbps** |

小电脑网口与雷达的实际协商速率为 **100 Mbps 全双工**。全双工表示两个方向可以同时传输，并不把单方向上限变成 200 Mbps。在不计任何协议开销的理想情况下，它单方向最多容纳：

$$100,000,000 \text{ bps} \div (1280 \times 720 \times 3 \times 8 \text{ bits}) \approx 4.52 \text{ fps}$$

现场 RGB 接收频率为 **4.4 Hz**，折合像素有效载荷约 **97.3 Mbps**，接近这一理论上限。

#### 实测数据对比验证

| 监测指标 | 修复前 | 修复后 |
| :--- | :---: | :---: |
| **彩色图更新率** | 4.4 Hz | 13.9 Hz |
| **原生深度更新率** | 0 Hz | 29.7 Hz |
| **对齐深度更新率** | 0 Hz | 14.2 Hz |
| **RGBD 心跳频率** | 0 Hz | 14.1 Hz |
| **彩色图接收延迟中位数** | 943.9 ms | 58.3 ms |
| **原生深度接收延迟中位数** | N/A | 42.1 ms |
| **物理有线网口发送速率** | 约 100 Mbps | **0.003 Mbps** |

恢复通信不等于每路都跑满 30 Hz：原生深度恢复到 29.7 Hz，但 RGB、对齐深度与 RGBD 心跳仍在 14 Hz 左右。这个结果说明断流得到了缓解，不能据此声称整个视觉处理链路已经没有其他瓶颈。

### DDS介绍

![ROS 2 通信分层与进程内路径](https://img.muelsyse.us/bed/paper-20261110-ros-layers-24212fd3eca3.png)

*图 5：ROS 2 的客户端库、RMW 与 DDS 通信分层。满足条件的进程内路径可以绕过 DDS 序列化；跨进程是否使用网络或共享内存，取决于所选实现及配置。*

DDS（Data Distribution Service）是 OMG 发布的分布式数据通信标准。ROS 2 通常借助 DDS 提供发现、发布订阅和 QoS 等能力，通过 Topic 与数据类型组织通信，并使用 **RMW（ROS Middleware Interface）** 将客户端 API 与具体中间件实现分开，从而在适配接口支持的范围内切换实现。与 ROS 1 常用的中心化 Master 发现方式相比，DDS 可以通过分布式发现建立端点联系（不过，ROS 1 的 Master 也不是所有业务数据的转发中心；节点建立连接后，业务数据通常直接传输，不能把 Master 故障等同于所有既有数据连接立刻断开）。DDS 实现之间常通过 RTPS 互通，UDP/IP 是常见传输方式，但并非 DDS 标准只允许这一种传输。

### Fast DDS vs Cyclone DDS

下表只梳理与本次问题有关的差异，不按这一次现场经历给两种实现划分绝对的适用场景。

| 评估维度 | Fast DDS | Cyclone DDS |
| :--- | :--- | :--- |
| 共享内存 | 支持共享内存传输与数据共享等机制；是否启用、是否减少序列化或复制，取决于版本、配置和消息条件。 | 支持情况与版本、构建及配置相关；本文不能把“同机通信”直接视为已启用共享内存。 |
| 网络接口与组播 | 可配置网络传输、发现与组播行为，应检查实际生效的配置。 | 有接口选择和组播策略配置；本次通过 `AllowMulticast=spdp` 避免了业务数据组播。 |
| 本项目遇到的现象 | 曾遇到 Action / Service 不响应，未保存足够材料确认具体机制。 | 外部图像订阅与百兆有线接口加入后出现断流，限制业务组播后恢复。 |
| 选型与验证 | 应验证具体版本下的功能、QoS、负载和故障恢复。 | 同样需要在完整节点拓扑与实际网络条件下验证，不能只测单个节点。 |

### ROS2 component

ROS 2 Component 将节点实现编译为可动态加载的库，由组件容器在同一进程中加载。它提供共享的地址空间，便于组织节点，也为减少图像复制创造了条件，但容器如何调度回调还取决于所选执行器，不能一概等同于“共用一个线程池”。相机发布、图像预处理、YOLO 推理这类连续处理大消息的节点，很适合检查是否能放到同一容器中；不过，**组件化与进程内通信是两个相关但不同的配置点**，除了把节点放在一起，还要为相关节点启用 `use_intra_process_comms`，并确认消息与 QoS 支持这条路径。

#### 组件化加速原理

满足进程内通信条件时，消息可以通过 C++ 对象的所有权转移或共享交付给本地订阅者，从而减少两类开销：

1. **消息复制**：使用兼容的发布与订阅接口时，可以转移 `std::unique_ptr` 或共享只读消息；是否仍需复制，取决于订阅者数量、回调签名和缓冲策略。
2. **序列化**：本地进程内交付可以绕过 DDS 的序列化与反序列化。若同时存在外部订阅者，发布者仍需为外部路径准备中间件消息。

因此，“Component 一开就完全零拷贝”不成立。要验证实际效果，可以参考 ROS 2 的进程内通信示例检查消息地址，再结合实际负载测量 CPU 使用、内存带宽和端到端延迟。

### 单播

单播把数据发给特定目的地址。在本文的同机场景中，发往本机地址的数据通常可由本地路由交付，发往远端主机则仍要使用物理链路。单播不会自动保证高吞吐或低延迟，如果存在很多远端订阅者且需要分别发送数据时，总流量反而可能增加；它在本例中的收益来自避免高带宽业务组播进入受限接口。

### 组播

IPv4 组播使用 `224.0.0.0` 至 `239.255.255.255` 地址范围。发送端向组播组发送数据，网络设备按照组播转发配置处理，接收端通过加入组播组来接收；交换机是否只向有成员的端口转发，还与 IGMP snooping 等功能有关，未启用或配置不当时，流量可能被泛洪到更多端口。组播适合一对多传输，但仍然受链路带宽、无线环境和端点实现约束。
