## 根因剖析

### 问题分析

小车接上雷达网络后摄像头断流，将 Cyclone DDS的`AllowMulticast` 改为 `spdp` 后深度图推流就恢复了，物理接口的发送速率也从约 100 Mbps 降到 0.003 Mbps。应证了**高带宽图像通过 DDS 数据组播进入有线网口百兆链路**这一解释。

我当时换成 Cyclone DDS 后没有立即遇到问题，是因为当时的通信拓扑还比较简单：相机与 YOLO 在同一个容器进程内，二者当时走的是走进程内通信；后来新加的 WebRTC 节点，它在另一个进程，需要通过 RMW/DDS 接收原始图像。Cyclone DDS 会根据接口能力、配置和发现到的对端选择网络路径，对于无线接口倾向于只使用发现组播，对于有线接口允许更广泛地使用组播；问题在于，允许数据组播的接口并不一定有足够带宽，但Cyclone DDS并不管这个。1280 × 720 的 RGB8 图像按 30 Hz 发布，带宽需求大约为 664 Mbps，已经远超100 Mbps 了，网口不堪重负啊

### 重点

看到这里你一定还有一个感到很奇怪、反直觉的地方：数据明明已经通过 USB 进入同一台电脑，为什么数据通信还会受到物理网口影响？

我来还原一下数据传输路线。摄像头数据通过USB进入了电脑，但是由于Linux的进程内存隔离机制。对于跨进程的数据传输， 相机驱动只能把数据交给DDS了。

Clyclone DDS根据自己的数据组组播策略会选择一个默认网卡，然后调用 Linux 的 `setsockopt` 函数，并传入 `IP_MULTICAST_IF` 参数。该指令强制要求内核将组播 Socket 绑定到指定网卡。内核会直接将组播数据包发送到目标网卡，并同时复制一份发到本地127.0.0.1.这里又有问题了，这个本地回环发送的前提是，前面那个发送到目标网卡的任务完成。我们这里深度和RGB数据太大了，直接给100Mbps的小水管挤爆了，本地回环也没法复制。

问题又来了，为什么这里本地回环也没法完成复制呢？这里又涉及到Linux 内核处理组播数据的链路。

1. DDS调用系统接口发送UDP数据时，内核会为数据包分配内存，并且扣除当前Socket的`SO_SNDBUF`缓冲区配额
2. 数据包进入内核的`ip_mc_output`函数之后，内核马上复制一份送到127.0.0.1，同时把原始数据包送入目标网卡的发送队列，这里两步是同步进行的
3. 这里有一个很大的问题，我这个时候图像速率远超网口的速率，大量数据包积压在发送队列，旧的没发出去，新的又来了，就算我缓冲区特别大也经不起这么耗啊(数据发出去之后缓冲区才会释放对应数据)。缓冲区满了，导致后续数据包在第一个阶段前(内核协议栈)就被丢弃了，连回环复制阶段都到不了。

这里顺便解释一下为什么不连有线网口就可以正常运行。在只有无线网卡的情况下，CycloneDDS只会在无线网卡上为发现节点开启组播，业务数据走单播。

## 解决方案

```bash
export CYCLONEDDS_URI='<CycloneDDS><Domain Id="any"><General><AllowMulticast>spdp</AllowMulticast></General></Domain></CycloneDDS>'
```

`AllowMulticast` 取值说明

| 取值      | 行为与注意事项                                                              |
| :------ | :------------------------------------------------------------------- |
| `true`  | 允许发现和用户数据使用组播；是否实际使用还取决于接口和对端情况。在带宽受限的网络上，需要检查图像等大话题的传输路径。           |
| `false` | 禁用该配置所控制的组播。默认的组播发现路径不可用，可通过 `Peers` 等单播发现配置建立联系；不能概括为“任何节点发现都彻底失效”。 |
| `spdp`  | 仅保留 SPDP 参与者发现组播，端点匹配和业务数据使用单播。本例中，它保留了方便的节点发现，也避免了向百兆接口发送图像数据组播。    |

### DDS介绍

![ROS 2 通信分层与进程内路径](https://img.muelsyse.us/bed/paper-20261110-ros-layers-24212fd3eca3.png)

*图 5：ROS 2 的客户端库、RMW 与 DDS 通信分层。满足条件的进程内路径可以绕过 DDS 序列化*

DDS（Data Distribution Service）是 OMG 发布的分布式数据通信标准。ROS 2 通常借助 DDS 提供发现、发布订阅和 QoS 等能力，通过 Topic 与数据类型组织通信，并使用 **RMW（ROS Middleware Interface）** 将客户端 API 与具体中间件实现分开，从而在适配接口支持的范围内切换实现。与 ROS 1 常用的中心化 Master 发现方式相比，DDS 可以通过分布式发现建立端点联系（不过，ROS 1 的 Master 也不是所有业务数据的转发中心；节点建立连接后，业务数据通常直接传输，不能把 Master 故障等同于所有既有数据连接立刻断开）。DDS 实现之间常通过 RTPS 互通，UDP/IP 是常见传输方式，但并非 DDS 标准只允许这一种传输。
### ROS2 component

ROS 2 Component 将节点实现编译为可动态加载的库，由组件容器在同一进程中加载。它提供共享的地址空间，便于组织节点。相机发布、图像预处理、YOLO 推理这类连续处理大消息的节点，很适合放到同一容器中；**不过，组件化与进程内通信是两个相关但不同的配置点，除了把节点放在一起，还要为相关节点启用 `use_intra_process_comms`，并确认消息与 QoS 支持这条路径。**
